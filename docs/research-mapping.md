# Phase 1 research-to-code mapping

Phase 1 resumed after the Phase 0.5 research approval. The references below were identified from the supplied PDFs and cross-checked against their publication records. All three supplied papers were available. Page numbers below refer to the supplied PDFs, with PDF page 1 as the first page.

## Published research

| Supplied paper | Methods relevant to ComputeTorrent |
| --- | --- |
| **Petals.pdf**. Borzunov et al., *Distributed Inference and Fine-tuning of Large Language Models Over The Internet*, NeurIPS 2023. [Proceedings](https://papers.nips.cc/paper_files/paper/2023/hash/28bf1419b9a1f908c15f6195f58cb865-Abstract-Conference.html). | Sections 3.2–3.3 and Algorithm 1 describe a latency-aware pipeline with server-side attention KV caches and client-side saved stage inputs. If a server leaves, a compatible replacement can reconstruct its cache from those inputs. Servers advertise block ranges and measured throughput in a DHT and rebalance ranges to relieve bottlenecks. The paper describes a client-mediated formulation and an optional direct stage-forwarding optimization. Its evaluation is on the paper's models, hardware and networks. |
| **Petals Paper 2.pdf**. Borzunov et al., *Petals: Collaborative Inference and Fine-tuning of Large Models*, ACL 2023 System Demonstrations, pp. 558–568. [ACL Anthology](https://aclanthology.org/2023.acl-demo.54/). | Section 3 explains cached generation, latency-aware client routing, quantization and selection of contiguous block ranges to improve the weakest-served blocks. The balancing signal combines measured compute and network throughput. The system also exposes hidden states for research and efficient fine-tuning. It supplies useful baselines for controlled bandwidth/latency experiments, rather than a performance target for this repository. |
| **Sun et al..pdf**. Tingyang Sun, Ting He, Bo Ji and Parimal Parag, *Optimizing Resource Allocation for Geographically-Distributed Inference by Large Language Models*. [Technical report](https://arxiv.org/abs/2512.21884) and [journal publication](https://www.sciencedirect.com/science/article/pii/S0166531625000616). | Section 2 separates first-token and subsequent-token costs, modelling per-block processing, client-to-server communication and model/KV memory. Section 3 formulates joint block placement and request routing (BPRR) as an offline MILP. Algorithm 1, CG-BPRR, conservatively sizes each worker for the target request count, places contiguous ranges in amortized server-cost order where service is most needed, then routes over feasible coverage with shortest paths. The online extension uses slower robust CG-BP placement and faster waiting-penalized shortest-path request routing (WS-RR). The waiting penalty accounts for when the route can obtain cache space. See PDF pp. 13–18 and Algorithm 2. |

Sun's conservative capacity model budgets block weights plus per-request cache memory. Its amortized worker cost combines per-block processing time and a worst-client per-token RTT divided by hosted block count. The online routing method uses active-session memory and estimated remaining time. These are model inputs and assumptions, not quantities the current coordinator already measures. The paper's guarantees are conditional on its model and feasibility/load assumptions. A CPU/Docker adaptation, a single-job experiment, and any deployment under churn need their own calibration and evidence.

## Implementation sequence for later approvals

1. **Phases 2–3, connectivity prerequisite.** Design and validate separate coordinator WebSocket, WebTorrent data, and Petals activation paths. The existing ngrok helper tunnels coordinator port 8001. It supplies no evidence that the Petals DHT bootstrap or stage TCP endpoints are reachable. Distinguish Docker-host addressing, LAN, Internet, NAT/CGNAT and direct/relay paths. Test actual activation reachability inside containers before allowing a worker into a route.
2. **Phase 8, measure and calibrate.** Establish a fixed model revision, runtime digest, device/dtype, prompt length and output limit. Collect cold and warm prefill/decoding timings, measured KV/weight/reserve memory, activation-sized transport costs and telemetry age. Use the coordinator as the client in the first experiment, consistent with the present topology. Build a reproducible fixture for unequal CPU/GPU capacities and missing links.
3. **Phase 8, plan without changing live jobs.** Replay captured or synthetic profiles through the current planner and a separate experimental CG-BP-inspired candidate at one request. Check that each feasible plan covers every block in order, obeys memory, respects reachability and selects compatible runtimes. Compare against exhaustive enumeration for small cases. Record reasons for rejected candidates and retain the existing planner as the default until the comparison is reviewed.
4. **Phase 8, isolated A/B execution.** Compare the two planners at identical model revision, prompt lengths, token limits, peer eligibility, verification policy, cache state, and network conditions. Report first-token latency, inter-token latency/tokens per second, end-to-end time, planner overhead, memory errors, completion rate, and verification results. Separate failures and excluded runs. Use repeated trials with distributions and no assumed speedup.
5. **Phases 8–10, optional route alternatives and recovery.** Before adding overlapping replicas, define a placement (what is loaded) separately from a request route (what actually ran). Keep verifier boundaries and provenance consistent with actual routes. Test loss of every stage and define fail-closed behavior when no replacement exists. Only evaluate waiting-penalized routing after multi-session admission and measured cache occupancy/remaining-time estimates are available.

The measurement schema, freshness policy, isolated A/B gate, fallback, and route provenance are **ComputeTorrent engineering proposals**. The Petals cache/rebalance design and Sun's CG-BPRR/CG-BP/WS-RR are published contributions. The proposed one-request adaptation is not a reproduction of Sun's full online method.

## Remaining decisions and risks

- Select the first supported model/device matrix, minimum hardware and test peer inventory before calibration. Confirm actual model compatibility rather than relying on catalog membership.
- Choose a credible trusted network baseline and approved remote test scenario. RTT alone can understate prefill costs under bandwidth limits, serialization overhead, asymmetric routes and congestion. Relay performance and data-path reachability require separate measurement.
- Decide whether capacity should optimize first-token latency, steady decoding, or bounded throughput under an explicit workload. Multi-session routing and redundant coverage consume resources and need separate acceptance gates.
- Set validation expectations for stale telemetry, Docker/driver compatibility, memory-estimation error, stage churn and verifier sensitivity to heterogeneous numeric execution. Preserve the existing verification decision and release restrictions.
- Runtime benchmarks, multi-peer recovery and external reachability are unverified in this phase. Phase 0.5 approval covers research only. Provider migration and production release gates remain in the [readiness checklist](provider-release-readiness.md).


## Sun optimization checkpoint — 2026-11-08

Implemented the operator-requested CG-BPRR/CG-BP, shortest-path/WS-RR, cache admission, request-target tuning, conditional bounds and bounded optional MILP reference kernels. Added a measured single-job coordinator bridge with baseline fallback/dominance gating and real gateway stage timings. See [Sun implementation and evidence](sun-optimization.md) for equation-to-function mapping, research attribution, assumptions, tests and outstanding gates.

58 selected tests passed. Two isolated native Petals fixtures (BLOOM and Llama/GQA) executed unequal 3+1 ranges with successful production generation and existing checks. Synthetic planner costs are not measured speedups. Candidate Docker images built/imported successfully; live containers were not restarted and updater/provider distribution settings were unchanged. The runtime still admits one job and materializes processed ranges only. Persistent replica pools, concurrent online scheduling, real pretrained heterogeneous-peer A/B performance, physical multiple-PC/CGNAT acceptance and production readiness remain unverified. Phase 8 is partially implemented and isolated-validated, not complete.
