# Phase 2 network design

## Evidence and diagnosis

This design separates four paths. A green status on one path does not imply readiness on any other.

| Path | Current entry points | Failure modes and diagnostic |
| --- | --- | --- |
| Coordinator control | HTTPS enrollment and WebSocket registration/heartbeat on 8001. `start-ngrok.ps1` forwards HTTP 8001. Portal `pages/api/provider-address.ts` reads a saved tunnel or the inspector. | Wrong tunnel target, stale URL, failed TLS/upgrade, invalid credential, missing registration acknowledgement. The script takes the first HTTPS tunnel without matching the upstream, and portal discovery can return an unverified cached URL. Probe the configured target, then require registration acknowledgement. |
| LAN overlay | `07-network-layer/src/libp2p_network.js` exposes TCP 9100, mDNS, Kademlia, Noise and Circuit Relay v2. The DHT uses a public-address removal mapper. The provider launches its helper independently of its WebSocket. | mDNS depends on local multicast. Guest Wi-Fi, VLANs and Docker Desktop may prevent discovery. Verify explicit bootstrap and peer identity from the helper, and never infer data transfer from overlay status. |
| File transfer | `swarm_service.js` seeds private WebTorrent swarms. Provider helper uses tracker signalling and verifies artifact hashes. | Tracker availability, incompatible peer transports, restrictive NAT/firewall, or missing seeder. Check actual bytes and digest. A relay reservation in the separate overlay does not prove a usable WebTorrent route. |
| Petals activations | `petals_control.py` starts a container exposing TCP 31330 and prepares advertised addresses. `gateway.py` advertises TCP 31331. `bootstrap_probe.py` handshakes in the worker, and `generate_job.py` checks stage route coverage. | Host bootstrap reachability is insufficient. Validate worker-to-DHT and gateway-to-worker RPC from the actual containers. Current gateway/worker configuration disables automatic relay, NAT mapping and AutoNAT. Current worker announcements accept IPv4/DNS TCP, and the gateway constructs an IPv4 announcement. |

The reported ngrok failure cannot be assigned to a specific live incident from this checkout. The prior checkpoint recorded no active local tunnel. This phase again found no ngrok process or saved tunnel file. A source-level limitation is clear: the HTTP tunnel can carry control, but it does not expose the other three paths. LAN addresses advertised through that tunnel generally cannot be dialed by Internet peers. On one host, Docker host aliases must refer to that host only. Across LAN machines use addresses actually reachable from each container. IPv6, hairpin NAT, split DNS, changing NICs, and duplicate private subnets need explicit validation. No external endpoint was probed.

## Protocol decision

| Option | Selected use | Trade-off |
| --- | --- | --- |
| HTTPS/WSS | Stable authenticated enrollment, control and rendezvous over outbound 443. ngrok remains an optional development control tunnel after target verification. | Widely usable, but some proxies block WebSocket upgrades. Control readiness proves no data route. TLS may terminate at an ingress, so secure its upstream and restrict exposed paths. [ngrok WebSocket documentation](https://ngrok.com/docs/using-ngrok-with/websockets) |
| Direct TCP | Preferred Petals path for trusted LAN or explicitly authorized, positively probed endpoints. Preserve Hivemind RPC and native sessions. | Fewer hops and no relay traffic. Requires bidirectional functional reachability for the topology, and appropriate firewall policy. No automatic router changes. |
| ICE/STUN/TURN | Evaluate for the WebTorrent/WebRTC path. ICE tests address pairs, STUN can discover mapped addresses, TURN relays when direct connectivity fails. | STUN alone cannot solve all NATs. TURN introduces capacity, credentials and egress cost. Validate the pinned WebTorrent client's ICE configuration before assuming compatibility. This does not make native Petals TCP traversable. [ICE RFC 8445](https://www.rfc-editor.org/rfc/rfc8445.html) and [TURN RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html) |
| libp2p Circuit Relay v2 | Keep for the discovery overlay. Evaluate native Hivemind relay only as a separately validated option. | Relay reservations and peer transport support are required. Existing JS overlay configuration provides no evidence of compatibility with the pinned Hivemind daemon or its routing/limits. [Circuit Relay v2 specification](https://github.com/libp2p/specs/blob/master/relay/circuit-v2.md) |
| Authenticated reverse streams over outbound WSS | **Selected Petals fallback design.** Use a managed ingress plus app-scoped connectors to carry native TCP bytes without changing Petals framing. | Works in principle behind double NAT/CGNAT when outbound WSS is permitted. It adds a network hop, extra bandwidth and TCP head-of-line risk. Container-visible addressing and peer identity must pass a prototype before remote placement is enabled. |

## Target topology and connection workflow

1. **Enroll.** Provider receives an operator-approved coordinator identity and stable HTTPS origin. Require valid certificates and a short-lived single-use enrollment invite. Bind a revocable node credential and provider proof-of-possession key to the workspace. Keep credentials local and never reuse the release signing key. The existing default join fallback, broad tunnel exposure and unauthenticated bootstrap information require hardening before remote enablement. Keep operator endpoints private and legacy updater routes retired.
2. **Connect.** The native provider already supports enrollment, a WebSocket and heartbeat. Add an authenticated route descriptor and per-transport state. Exchange protocol revision, worker identity, candidates and lease epoch. Verify the runtime peer ID by challenge over an authenticated path before assigning work. LAN discovery is a candidate hint and cannot change the trusted coordinator or bypass credentials.
3. **Probe direct first.** Try a bounded list of authorized endpoints concurrently with deadlines. Run real Hivemind bootstrap and stage RPC probes from worker and gateway containers, verify expected peer IDs, and cache the result only for a short lease. Do not perform arbitrary IP scans, expose raw public worker ports, or trust a peer-supplied destination.
4. **Use the relay when direct fails.** Both provider and coordinator connectors make outbound TLS-verified WSS connections to an approved relay. The relay authorizes a workspace/job/peer-scoped stream from the gateway to a provider worker and a reciprocal worker-to-gateway bootstrap stream. Each connector opens only its approved local Docker endpoint. Use separate streams or bounded fair multiplexing, byte backpressure, connection timeouts and explicit FIN/reset handling. Keep native Hivemind encryption and identity end to end. The broker maps authenticated route IDs, never arbitrary host/port requests. Test DNS or proxy addresses scoped to each authorized container network. Provide a stable mapped listener per peer/lease reachable by the gateway, plus a worker-visible bootstrap mapping. Advertised multiaddresses must reach those listeners and retain the actual destination peer ID. Replacing an address inside only the host app is insufficient.
5. **Admit only reachable routes.** Expose states such as control online, file route ready, Petals direct ready, Petals relay ready, and unavailable. Feed verified path type, age, measured activation RTT and reachability to later placement work. If both paths fail or egress WSS is blocked, keep the provider connected for diagnostics and exclude it from affected jobs. For file transfer, keep current WebTorrent first; if TURN is unsupported or unavailable, evaluate a separately authorized, hash-verified resumable HTTPS artifact path with job-scoped URLs. The update feed is independent.
6. **Reconnect safely.** Apply bounded exponential backoff with jitter, renew or revoke short-lived leases, re-probe on address/identity change, and reject obsolete connection generations. Prefer a proven direct route for new work, with hysteresis. Do not move an active Petals session between paths unless cache/session recovery is verified. Otherwise fail with a reason and release reservations. Report readiness only after handshake and route coverage.

## Security, performance and operations

Only approved ingress endpoints are public. Separate workspace, node and job identities. Bind relay tickets to direction and permitted peer, cap streams, bandwidth, byte totals and lease duration, and prevent arbitrary forwarding or loopback/metadata-service access via caller-selected targets. Log auth failures, route type, lease changes and transfer counters without credentials, private prompts or activations. Require rate limiting, credential revocation and a tested relay shutdown path. Relays observe timing and volume, while the native encrypted session must remain opaque. Volunteer execution still has the existing model/activation trust boundary.

Measure connection setup time, direct/relay success rate, p50/p95 activation RTT and prefill throughput, tokens/sec, reconnect time, transferred bytes and relay utilization. Separate warm from cold cache and test under load. Budget relay egress from measured forwarded bytes and approved host pricing; include both activation directions, file volume if TURN is used, fixed host cost and monitoring. Apply explicit concurrency and spend ceilings before wider tests. Single relay is a failure domain; make failure visible and defer redundancy until measured demand. No latency, cost or availability target is claimed from source inspection.

## Migration and Phase 3 acceptance gates

- The current tracked project has no mandatory Tailscale dependency. Retain any privately configured tailnet only as an operator-controlled compatibility route during comparison. Volunteer onboarding should need an approved invite and outbound access after the new path passes tests. No existing VPN configuration is changed.
- Implement opt-in LAN diagnostics and identity/lease hardening first. Then prototype the private reverse-stream mapping using pinned containers. Verify that gateway routing reaches the correct worker, the worker can bootstrap, and every stage can complete a small inference. If the pinned runtime cannot use the proposed addresses safely, keep remote Petals disabled and bring the transport decision back for review.
- Test same host, same Wi-Fi, separate LAN devices, separate Internet providers/CGNAT, blocked inbound, blocked UDP, WSS proxy, stale DNS, wrong peer ID, expired/revoked ticket, relay outage and reconnect. Verify file digest, negative auth cases, duplicate assignments and failure reporting. Test direct/relay performance and cost separately.
- Existing upstream code and ngrok helper remain in place. Public endpoints, relay provisioning, production deployment and provider releases require their own approvals. Keep legacy updater restrictions and migration gates active.

Phase 2 validation was a source/protocol review and the four existing Petals network unit tests, which passed. Live tunnel behavior, cross-network inference, relay interoperability and capacity remain Phase 3 or later verification.
